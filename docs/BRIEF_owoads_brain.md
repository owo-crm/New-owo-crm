# Бриф: «мозг» OWO Ads — собственный кабинет агентства

> Для сессии Claude Code в репозитории `owo-crm/New-owo-crm`.
> Прочитай этот файл целиком, потом `docs/` и схему в `db/migrations/`, и только потом предлагай план.
> Все тексты интерфейса — по-польски, через `messages/pl.json`. Комментарии в коде — по-русски, как во всём проекте.

---

## 1. Что строим и зачем

В CRM уже есть мультибизнес: одна установка, много организаций, разделение данных через RLS в Postgres.
Barowo — первый бизнес, он настроен и работает.

Теперь нужен **кабинет самого OWO Ads** — организация, в которой агентство ведёт не свадьбы, а
**собственное агентство**: своих клиентов, свои деньги и настройку CRM для этих клиентов.

Это не новый продукт и не отдельное приложение. Это:
- вторая организация в той же установке (`industry_preset = 'agency'`),
- плюс несколько экранов, которые видны **только** в организации с этим пресетом,
- плюс связь «клиент агентства → его организация в CRM».

**Главный критерий готовности:** владелец агентства открывает один экран и видит,
сколько заработано, кто сколько должен получить и что осталось донастроить у каждого клиента.
Сейчас этого нет нигде — ни в коде, ни в таблице.

---

## 2. Чего делать НЕ надо

Это важнее списка задач. Не трать время на:

- **Отдельные копии CRM под клиента.** Решено: одна установка, переключатель бизнесов. Поддомены тоже отклонены.
- **Прайс-лист как справочник услуг с фиксированными ценами.** Прайса ещё нет, цены каждый раз договорные. Цена вводится руками в карточке заказа.
- **Автоматические выплаты, интеграцию с банком, генерацию фактур.** Пока только расчёт и таблица «кому сколько».
- **Отдельную систему учёта часов.** Часы вводятся прямо в карточке заказа, строкой на исполнителя. Таймеров, трекеров и календарей времени не делать.
- **Переделку существующих экранов Barowo.** Новые экраны не должны ничего ломать в `event-services`.

## 4. Модель данных

Новая миграция, одна. Пресет `agency` у организации включает все экраны ниже.

### 4.1 `agency_clients` — клиент агентства

Связывает карточку клиента с его организацией в CRM, если мы ему её завели.

```
id, organization_id (= организация OWO Ads)
name, nip, contact_name, phone, email, city
client_org_id uuid null   -- организация клиента в этой же установке, если CRM ему выдана
status: 'lead' | 'active' | 'paused' | 'lost'
started_at date, note text
```

`client_org_id` — обычный внешний ключ на `organizations(id)`. Он и есть мост между
кабинетом агентства и CRM клиента.

### 4.2 `agency_orders` — проданная услуга

Одна строка = один проданный заказ. Абонемент = строка на каждый месяц (так проще считать
и так видно, что месяц оплачен).

```
id, organization_id, client_id
title text                    -- «Pakiet Start, listopad» / «Landing page»
kind: 'retainer' | 'project'
amount_grosze bigint          -- цена netto, вводится руками
direct_costs_grosze bigint    -- подрядчики, печать, шаблоны, дальние поездки
ad_budget_grosze bigint       -- бюджет клиента на Meta/Google. В раздел НЕ входит, хранится для отчёта
sold_by uuid                  -- кто нашёл и закрыл
period_month date null        -- для абонемента: первое число месяца
status: 'draft' | 'invoiced' | 'paid' | 'cancelled'
paid_at timestamptz null
```

### 4.3 `agency_order_work` — кто сколько сделал

```
id, organization_id, order_id
user_id uuid, hours numeric(6,2) check (hours > 0 and hours <= 500)
note text
```

### 4.4 Функция раздела — единственное место, где живёт формула

```sql
public.agency_order_split(p_organization uuid, p_order uuid)
  returns table (user_id uuid, role text, amount_grosze bigint)
```

Правила (из `07_Partnership_Model.md`, раздел 1):

```
база = amount_grosze − direct_costs_grosze      -- ad_budget_grosze не участвует никогда
10 % базы → sold_by                              (role = 'sale')
25 % базы → компания, user_id = null             (role = 'company')
65 % базы → исполнителям пропорционально часам   (role = 'work')
```

- Если один и тот же человек продал и сделал — он просто получает обе строки (суммарно 75 %).
- Если часов не записано ни одного — 65 % идут строкой `role = 'work', user_id = null`
  с пометкой «не распределено». Не прячь это и не отдавай компании: нераспределённые деньги
  должны быть видны, иначе их забудут.
- Округление: считай в грошах целыми, остаток от деления отдавай компании. Сумма строк
  обязана совпадать с базой до гроша — напиши на это тест.
- Проценты вынеси в константы в одном месте (`lib/agency/split.ts` + значения по умолчанию
  в колонках организации), чтобы менять их без правки формулы.

### 4.5 `agency_setup_steps` — этапы настройки CRM клиента

Чек-лист, одинаковый для всех, со своим состоянием у каждого клиента.
Шаги заводит миграция (таблица-справочник или `enum` + таблица отметок — на твоё усмотрение,
но справочник лучше: шаги будут меняться).

Стартовый список шагов, в этом порядке:

1. `org_created` — организация клиента создана
2. `service_member` — участие OWO Ads помечено обслуживающим (`mark_service_membership`)
3. `branding` — название, цвет, логотип, реквизиты
4. `stages` — воронка под отрасль клиента
5. `intake_channel` — канал приёма заявок создан, домен клиента в `allowedOrigins`
6. `form_connected` — форма на сайте клиента шлёт заявки, пришла хотя бы одна настоящая
7. `documents` — шаблоны оферты/договора под клиента
8. `notifications` — Telegram и/или почта подключены
9. `owner_invited` — ссылка-приглашение с ролью `owner` отправлена
10. `owner_joined` — владелец вошёл сам
11. `handover` — показали, как пользоваться

У каждой отметки: `done_at`, `done_by`, `note`.

**Шаги 1, 2, 5, 6, 9, 10 отмечай автоматически**, по фактам в базе, а не руками:
- `org_created` — существует `client_org_id`;
- `service_member` — есть `memberships.is_service = true` в организации клиента;
- `intake_channel` — есть `channels` типа `website` со статусом `active`;
- `form_connected` — в `intake_log` есть успешная запись (`ok = true`);
- `owner_invited` — есть приглашение с ролью `owner`;
- `owner_joined` — в организации клиента есть участник `owner`, кроме аккаунтов OWO Ads.

Ручные отметки — только там, где факт в базе не виден (`branding`, `documents`, `handover`).
Это принципиально: ручной чек-лист перестают заполнять через две недели.

## 5. Экраны

Все — только при `industry_preset = 'agency'`. Пункты меню для других организаций не показывать.

### 5.1 `/agencja` — главный экран, тот самый «мозг»

Сверху четыре плитки за выбранный месяц:
**Выставлено · Получено · Ожидается · Просрочено.**

Ниже три блока:

1. **Раздел средств за месяц.** Таблица: человек → за продажи → за работу → итого;
   отдельной строкой компания (25 %) и, если есть, нераспределённое. Внизу — итог,
   который обязан сходиться с «Получено».
2. **Клиенты.** Строка на клиента: название, статус, сумма за месяц, прогресс настройки
   («7 из 11»), последняя активность. Клик — карточка клиента.
3. **Что требует внимания.** Неоплаченные заказы с просроченным сроком, клиенты без заказов
   в этом месяце, незаконченная настройка старше 14 дней.

Переключение месяцев — как на `/finanse`, переиспользуй там же лежащие помощники.

### 5.2 `/agencja/klienci/[id]` — карточка клиента

- Реквизиты и контакт.
- Чек-лист настройки с автоматическими отметками и кнопкой «Открыть CRM клиента»
  (переключает организацию на `client_org_id`).
- Заказы клиента: список, суммы, статус оплаты, разбивка раздела по каждому.
- История: что и когда делали.

### 5.3 `/agencja/zlecenia/nowe` — новый заказ

Форма: клиент, название, тип, сумма netto, прямые расходы, рекламный бюджет, кто продал,
строки «исполнитель + часы». **Расчёт раздела показывается прямо в форме, до сохранения** —
это главное в экране: человек должен видеть, сколько он получит, пока вводит цену.

### 5.4 Лиды самого агентства

Отдельных сущностей не заводить. Лиды с лендинга OWO Ads приходят в эту же организацию
через существующий `/api/intake/<key>` и живут в обычной таблице `leads`.
Нужно только:
- воронка под агентство (`pipeline_stages` для пресета `agency`):
  `nowy → kontakt → spotkanie → oferta → klient → odrzucony`;
- на этапе `klient` — кнопка «Завести клиента агентства», которая создаёт `agency_clients`
  из лида и связывает их.

В `landing/index.html` после этого надо проставить `INTAKE_URL` — там для этого уже оставлено место.

## 6. Порядок работы

Делай по одному куску, с тестами и деплоем на каждом шаге, не всё сразу.

1. Миграция: таблицы, справочник шагов, RLS, функция `agency_order_split`, пресет `agency`.
   Тесты в `tests/db/`: раздел сходится до гроша, нет часов → нераспределённое,
   рекламный бюджет не влияет, чужая организация ничего не видит.
2. `lib/agency/*`: чтение, запись, расчёт. Тесты на формулу отдельно от базы.
3. Экран `/agencja/zlecenia/nowe` с живым расчётом.
4. Экран `/agencja` со сводкой и разделом.
5. Карточка клиента и чек-лист с автоотметками.
6. Воронка агентства и кнопка «завести клиента из лида».

После каждого шага: `npm test`, `npm run build`, `npx prettier --write .`, коммит, пуш.
Railway выкатывает сам и прогоняет миграции при старте — проверяй логи деплоя.

## 7. На что обратить внимание

- **Проценты 65/25/10 не утверждены партнёрами.** Поэтому они обязаны быть параметром, а не
  числом в коде. Если спрятать их в формуле, при первом же пересмотре придётся переписывать расчёт.
- **Часы — слабое место схемы.** Если их не заполнять, 65 % некуда распределять. Поэтому
  поле часов должно быть в той же форме, что и цена, а не на отдельном экране.
- **Абонемент.** Ежемесячная строка на клиента — это ручная работа каждый месяц. Сделай
  кнопку «повторить заказы прошлого месяца», иначе этим не будут пользоваться.
- **Не смешивай с `lead_payments`.** Там деньги клиентов Barowo за мероприятия, здесь —
  деньги агентства за услуги. Таблицы разные, экраны разные.
- Проверь работу на обеих темах (светлая/тёмная) и на телефоне: e2e-тесты в `tests/e2e/`
  гоняются в двух размерах, добавь туда и новые экраны.
